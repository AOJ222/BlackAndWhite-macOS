# Black & White.app

A double-clickable macOS app that starts the native Black & White builds (`native/bw-native`,
the original code lifted to run on Apple Silicon): the 1.00 build for an unpatched copy of
the game, and the Fan Patch 1.42 build for a patched one. This is the released app: it holds
no game content, and it does nothing until the player adds their own copy of the game.

## The short way (playing)

1. Put `Black & White.app` (and `Black & White Settings.app`, if you want it) in Applications.
2. Open it. The first start shows **Add Your Disc**: choose the `.iso` image of your Black &
   White disc, a folder that is a copy of the disc, or the folder the game is installed in.
   The app reads what you chose, checks the game's files against `game-manifest.json`, and
   builds its game folder under `~/Library/Application Support/Black & White`. What you chose
   is only read and is not needed again. Set-up takes under a minute and about 3 GB.
3. Press **Play Black & White**. Every later start goes straight to the game.

Supported: any complete copy of the game — the original disc as sold, a patched copy
(1.10/1.20, the Fan Patch), or another language edition. The program files are generated by
the app at set-up, so no copy is refused for carrying a different program; the game content
is checked file by file (the files a patch or a language changes are accepted in any of their
known forms). An unpatched copy plays the 1.00 build; a patched one plays the Fan Patch 1.42
build (the 1.42 program is the patched program a 1.10/1.20 copy is updated to). A copy that
is incomplete or not the game is refused with a plain message and nothing is set up.
Creature Isle, the expansion, is not supported yet: its discs and folders are refused with
a plain message (a folder with the expansion installed in it sets up the base game it
holds). Requirements: Apple silicon, macOS 27 (this build), about 3 GB free.

## Building it

```
python3 native/app/build-app.py --release --out <folder>   # the copy for other Macs
python3 native/app/build-app.py --install                  # this Mac (keeps using its own game files)
```

`--release` names no game folder or disc copy of the building Mac in `defaults.conf`, so the
app's first start is always the add-your-disc step. Without it, the app uses the folders
`stage-game.py` or `import-game.py` already made on this Mac. The first start needs no
Terminal and no tools of the Mac's own: the disc importer runs inside the app (the compiled
front door, `frontdoor/`, with `unshield` bundled). `import-game.py` remains as the same
import from Terminal (it needs `unshield`, which it does not install: `brew install unshield`),
and `tests/frontdoor.sh` exercises the in-app one.

Then open `~/Applications/Black & White.app` from Finder, Launchpad or the Dock. A start takes
the mouse and keyboard for the game, as the foreground runs of `bw_native` do.

The screen, resolution, frame limit and sound are chosen in `~/Applications/Black & White Settings.app`
(built and installed beside the game; see "The Settings app" below) before the game is started, not by
editing a hidden file. While you play, the Screen and Resolution choices are in the game's own Options
screen as well, with a Sound switch and a Master Volume of the port's (Esc, then the Options tab; see
"In the game" below).

## First start on macOS (Gatekeeper)

The app is signed ad hoc (`codesign -s -` in `build-app.py`); it is not notarised. An app
built on this Mac carries no quarantine mark and opens normally. A downloaded one may be
refused by Gatekeeper on its first launch. Open System Settings → Privacy & Security, scroll
down and click **Open Anyway**, then **Open** (Apple's "Safely open apps on your Mac"). Or
clear the quarantine mark first:

```
xattr -dr com.apple.quarantine "$HOME/Applications/Black & White.app"
```

Use the real path of the app if it is somewhere else.

## Why the game files are copied (`stage-game.py`)

macOS keeps `~/Desktop`, `~/Documents`, `~/Downloads` and other drives private from each app until
the user lets it in. An app whose main program is a shell script cannot even be asked: the system log
shows the request attributed to `/bin/bash` and answered with "auth_value absent", and every read ends
as "Operation not permitted". A game folder on the Desktop, which reads fine from Terminal, is therefore
unreadable when the app is started from Finder. (Seen on this Mac, 2026-11-08: the first start
through `open` stopped at the check of `runblack.exe`.)

`stage-game.py` copies the game folder and the disc copy to
`~/Library/Application Support/Black & White/` (`Game`, `Disc`, `Disc.volume`), which any app may read.
On the same APFS volume the copies are clones: they share the originals' disk blocks until a file
changes, so the 1.3 GB cost about 1 MiB of disk and took a fraction of a second. It checks that the
copy has the same number of files and bytes, refuses to overwrite a different earlier copy without
`--replace`, and, if the folders were on another volume, would need a full copy and refuses when that
would leave under 15 GiB free.

`stage-game.py` copies an install folder and a disc folder that are already on disk. To start from the
disc image instead, use `import-game.py` (next section).

If the game folder the app is set up to use is under one of those private folders anyway, the start stops with
a message that says so, instead of a misleading "no runblack.exe".

## Importing from the disc image (`import-game.py`)

```
python3 native/app/import-game.py --iso ~/Downloads/BNW.iso        # into ~/Library/Application Support/Black & White
python3 native/app/import-game.py --iso BNW.iso --dest <folder>     # or somewhere else
python3 native/app/import-game.py --iso BNW.iso --replace           # again, replacing an earlier import
python3 native/app/import-game.py --check "<folder>/Game"           # check a game folder; changes nothing
```

The image is your own copy of the game (an ISO 9660 image); an installed copy of any version
can be used instead (`--folder`), as can a folder that is a copy of the disc (`--disc`).
The script reads the image without mounting it, puts the disc's files in `Disc` (read-only, with `Disc.volume`), unpacks
the installer's cabinets with `unshield` (`brew install unshield`; it is not installed for you) and builds `Game`
as `game-manifest.json` says. The manifest lists, for each of the game folder's 1,063 content files, where it comes
from on the disc, its size and its SHA-256 (paths and hashes only, no game data), and every file is checked as
it is made; the five program files are generated from the files the build was made from, never taken from the
player's copy. If a content file is missing or is not one of its known forms, nothing is put in place and the
script says which. The folder is the install layout that the installer makes, plus the music an install leaves
out. `make-game-manifest.py` writes the manifest from a folder known to work and the other versions' folders.

Checked on this Mac (2026-11-11): the in-app importer set the game up from a retail-style disc
folder with no program file on it, from the disc image, and from installed 1.20 and Fan Patch 1.42
folders; each result checked out at 1,068 of 1,068 files (1,063 content + 5 generated program
files), and the 1.20 and 1.42 setups started and played the intro.

Checked on this Mac (2026-11-11, for the 0.3.0 release): the release app's importer set the
game up from the disc image (recorded as Black & White 1.00) and from an installed Fan Patch
1.42 folder (recorded as Fan Patch 1.42); the launcher's dry run started `bw_native` for the
first and `bw_native_142` for the second, and the bundled `bw_native_142` ran from inside the
app and played the intro with no `FATAL` line. A Creature Isle disc copy was refused and the
base game already set up was left as it was.

Checked on this Mac (2026-11-09): an import of the image into a scratch folder took 5 seconds and all 1,068
files matched the manifest. The result was identical, file for file, to the staged copy that the parity runs
use, except two textures (`Data/Textures/PlayersSymbols.raw` and `PlayersSymbolsa.raw`, which the game seems to
write to) and two leftovers of earlier runs (`MemoryLeaks.txt`, `Profiles/`); the disc copy and `Disc.volume`
were identical to the earlier ones, byte for byte.

## Build it (`build-app.py`)

```
python3 native/app/build-app.py            # writes native/app/out/Black & White.app and Black & White Settings.app
python3 native/app/build-app.py --install  # and copies both to ~/Applications (not while either is running)
python3 native/app/build-app.py --force    # build although a build (ninja or cmake) is running
```

Options: `--build-dir` (default `native/bw-native/build/release`), `--out`, `--game-dir` and
`--disc-dir` (the folders written into the app as its defaults; without them the copies made by
`stage-game.py`, or, if there are none, the repository's `native/run/game` and `native/run/cd`).
`--build-dir-142` (default `native/bw-native/build-142`) names the Fan Patch 1.42 build folder.
The Creature Isle build (`--build-dir-ci`) is bundled only with `BW_INCLUDE_CI=1`; it is not
part of a release yet, and the front door refuses the expansion with or without it.

The script:

1. refuses to start with under 12 GiB free (and warns under 15 GiB); refuses while a build is
   running (unless `--force`); and refuses if `bw_native` changes during a pause of a second and a half
   before it is read, so a program that is still being linked is not packed;
2. copies `bw_native` and every non-system library it needs (SDL3, ffmpeg and what ffmpeg pulls in,
   the recompiled-code libraries, shader tools; 35 at the time of writing) into the bundle and points
   each one at the bundled copies (`install_name_tool`, `@rpath`). The program itself is never
   re-linked, because the lifted game needs the low 4 GiB of address space that its `__PAGEZERO` reserves;
3. signs everything ad hoc (`codesign -s -`), which is what a locally built app needs on Apple Silicon;
4. draws the icon (`Contents/Resources/AppIcon.icns`, see "The icon" below), and writes
   `Contents/Resources/BUILD-INFO.txt` (build time, source revisions with a note when they had
   uncommitted changes, the SHA-256 and write time of `bw_native` as built, the write time of the
   newest library built in this repository, the library count, and a note when a source file of either
   tree (code and CMake files, not tests, tools or notes) was written after the newest part of the
   build) and `defaults.conf` (the game folder and the disc copy; no program is pinned there —
   the program a start insists on follows the version the player's set-up recorded);
5. checks the result: `codesign --verify --deep --strict`, `Info.plist` names an icon file that unpacks to
   its ten pictures, every dependency is a system library or a bundled `@rpath` one, the run paths are
   exactly the intended ones, and the bundled `bw_native --help` starts and exits 0;
6. builds `Black & White Settings.app` beside it from `settings/BlackWhiteSettings.swift` (`swiftc`, system
   frameworks only; the game's icon), signs it ad hoc and checks it the same way, running its own checks
   (`--selftest`) from inside the finished bundle.

The apps are built in a hidden folder and renamed when complete, so a failed build never replaces a
working app. It does not build `bw_native`; build that first, and build the app again to pick up a newer one.

## The icon

A macOS icon tile (824 of the 1024 units, with the smooth corners of Apple's own tile) cut corner to corner
into a black half (lower left) and a white half (upper right). Across the cut sits the game's logo: the
dragon and the idol, with BLACK & WHITE in the game's lettering. The logo is drawn once, by inverting what
is under it, so it is white on the black half and black on the white half with no seam where they meet.
The dragon's eye is the one spot of colour. Edge light, a soft shadow on the white half, a faint glow and a
glossy streak on the black half, and a hairline of warm light along the cut give it depth.

The logo is the game's own artwork, so it stays out of git: `native/app/icon-art/logo-art.txt` (about
100 KB of curves) is ignored by the allow-list in `.gitignore` and stays on this Mac with the game files.
The game has no large copy of its logo (its `.ico` files are 32×32 pixels in 16 colours), so
`tools/trace-bw-logo.py` makes the file from the two pieces that survive: `bw-game/Scripts/html/bwlogo.gif`
(the emblem, without lettering) and the native port's title screen (`native/run/shots/m2/m2-title.png`,
which has the lettering), neither of them tracked. It needs numpy, OpenCV and Pillow, which the system's
`/usr/bin/python3` has and the repository's `.venv` does not, so run it with that interpreter:
`/usr/bin/python3 tools/trace-bw-logo.py --check` rewrites the file and reports how well the curves follow
the pictures (about 99% overlap for the emblem and the lettering).

Without that file (a fresh clone) or with `--plain`, the logo is replaced by one big ampersand from a system
typeface (Baskerville Bold, else Georgia Bold or Times Bold) and everything else is drawn the same.
`build-app.py` takes whichever it gets.

`make-icon.swift` draws the ten pictures an icon file needs; `build-app.py` compiles and runs it
(`swiftc`, which comes with Xcode's command line tools; with no options, so the logo file is used when it
is there), packs the pictures with `iconutil` and puts the result in the app. To look at the picture without
building the app (from the repository root, where the logo file is found; or name it with `--art`):

```
swiftc -O native/app/make-icon.swift -o /tmp/make-icon && /tmp/make-icon /tmp/bw.iconset
open /tmp/bw.iconset/icon_512x512@2x.png
/tmp/make-icon /tmp/plain.iconset --plain      # the typographic icon
```

To change it, edit `make-icon.swift`: the sizes, colours and strengths of the effects are at the top, and
`compose` applies them in order. `--font` names another typeface for the plain icon.
`python3 native/app/tests/icon.py` checks the drawing without the game, in both forms: the ten sizes, the
tile's size, corners and shadow, a white half, a black half, the logo inverted across the cut, the amber eye,
a damaged logo file refused, and a round trip through `iconutil`.
If Finder or the Dock go on showing an older picture after an install, `touch` the app and open its
folder again; logging out clears the system's icon cache.

## Controls on a Mac

Black & White is played with the mouse. On macOS:

- **Right button:** Control-click and Option-click are sent to the game as the right mouse button (the
  modifier chosen at press is kept through release; the system two-finger click also arrives as the
  right button).
- **Zoom:** Scrolling up and down with two fingers on the trackpad (or the wheel of a mouse) is the game's
  wheel, in whole notches (SDL's accumulated step), and it only zooms. Sliding the fingers sideways does
  nothing. A pinch gesture is the wheel too, one notch per one-eighth of a doubling in scale.

Details: `native/NOT-ORIGINAL.md` ("Mouse buttons and the trackpad"). `BW_TRACE_INPUT=1` logs input.

## Frame rate

With a person at the window the game shows at most 60 pictures a second. To change that, put
`FPS_CAP=n` in `settings.conf` (`0` means no limit). A `settings.conf` made by an earlier build does not
list the key: add the line yourself. (The same limit is the environment variable `BW_FPS_CAP`; automated
runs started with `BW_BACKGROUND=1` have none unless one is set.) The cap limits how often the game
draws, not how fast it plays: the game's turns run at about ten a second from the clock. See
`native/NOT-ORIGINAL.md` ("Frame rate").

On this Mac, with no cap, a hidden window, and the heaviest known Land 4 scene: about **108–128
pictures a second** at logical **1280×800** (classic); the **1440p** and **4k** picture presets (below)
measured about **114–128** and **112–127** in the same conditions. Those numbers are from automated runs,
not yet from a person playing in a foreground window.

## How to quit

Closing the window, Cmd-Q, choosing Quit from the Dock, or Alt+F4 all reach the game as a close
request (`WM_SYSCOMMAND` / `SC_CLOSE`), as on Windows. The game's handler sets its terminate flag;
the main loop acts on it during play, not during logos, movies, loading, or while the Land 1 opening
cinematic still holds control.

During those moments the game ignores the request, as the original does. On the first request a
timer starts: if the game is still running after `QUIT_GRACE_MS` milliseconds (`settings.conf`; default
15000; `0` means never) the app ends it, with status 0. When the game can stop, it ends itself about
1.1 s after the request (the check is in `native/NOT-ORIGINAL.md`). The environment variable is
`BW_QUIT_GRACE_MS`.

## What a start does (`launcher.sh`, the bundle's main executable)

1. Reads `defaults.conf` from the bundle, then `settings.conf` from
   `~/Library/Application Support/Black & White/` (created with every setting explained on the first
   start). The files are parsed as plain `KEY=value` lines with a fixed list of keys and are never run
   as shell, so nothing in them can execute.
2. Checks that the game folder has the four lifted libraries' originals, that the disc copy and its
   `.volume` label file exist, that macOS lets the app open them, and that the game program of the
   version the set-up recorded (`GAME_VERSION` in `settings.conf`) can be found with its pinned
   SHA-256: for the base versions `bw_native` or `bw_native_142` is started with the generated
   `runblack.exe` of the matching build (`runblack-decrypted.exe`, `runblack.exe` in the game
   folder, then `crack/runblack.exe` on the disc copy; an `EXE` in the settings must match as
   well). Anything missing stops the start with a dialog saying what and where.
3. Writes the screen size into the game's registry file (`data/bw/registry.txt`), creating the file in
   the runtime's own format if it does not exist and otherwise changing only the picture width and height lines
   (`screenw`, `screenh`).
4. Opens a log in `~/Library/Logs/Black & White/native-<date>-<time>.log` (newest ten kept) and starts
   `bw_native` with its output going there. If the run ends and the log contains a `FATAL` line, a
   dialog offers to show the log.

Settings (all optional; the Settings app writes the first six): `SCREEN_MODE`
(`window` the default or `desktop`; `exclusive` is still read), `RESOLUTION` (`1280x800` by default; the
game's own picture size), `PICTURE` (`classic` the default, or `native`; the older `1440p` and `4k` are still
read), `RENDER_SCALE` (`0.5`–`4`; empty or `auto` is Automatic, the display's own pixel density: 2 on a Retina
display, 1 on others, worked out at each start; how many times finer the world is drawn than the picture
size), `FPS_CAP` (pictures a second, default 60, `0` none), `AUDIO` (`device` or `off`), and, set by hand
only, `GAME_DIR`, `DISC_DIR`, `EXE`, `DATA_DIR`, `POINTER` (`absolute` or `virtual`, for the pointer work in
progress; empty means the runtime's default) and `QUIT_GRACE_MS` (default 15000, `0` none).

## The Settings app

`Black & White Settings.app` is the one place a player changes the above, so nobody has to find or edit a
hidden file. `build-app.py` builds it with the game and `--install` puts it beside the game in
`~/Applications`. The game reads its settings once, when it starts, so a change is used the next time the
game is opened; the original asks for the same ("The video detail setting which you have chosen will only
take effect next time you start Black & White", from its own text).

| Setting | Choices | What it does |
| --- | --- | --- |
| Screen | Window; Full screen | `SCREEN_MODE` `window` or `desktop` (the display-switching `exclusive` is shown only when the file already asks for it) |
| Resolution | one list of seven sizes and "Match this display", each **named by the pixels the game draws**: on a Retina display 1440p (2560 × 1440), 2560 × 1600 (recommended), 2880 × 1800, 3360 × 2100, 4K (3840 × 2160), 3840 × 2400, 2048 × 1536 | `RESOLUTION` (the game's own picture size: more of the world on screen, smaller buttons) with the sharpness below. The name is the size times the sharpness, so 4K is the 1920 × 1080 picture drawn twice as fine. "Match this display" is the display's size in points as even numbers, worked out at each start |
| Advanced: Sharpness | Automatic, 1×, 1.5×, 2×, 3× | `RENDER_SCALE`. Automatic (the default) is the display's own pixel density, 2 on a Retina display and 1 on others, so the window is as many points as the picture has pixels; the numbers draw the world that many times finer than the picture, and in a window the window grows with it. The list is closed unless the file holds a sharpness that is not Automatic |
| Frame rate limit | 30, 60, 120, no limit | `FPS_CAP`. The game's own speed does not change |
| Play sound | on, off | `AUDIO` |
| Master volume | 0 to 100 | `VOLUME`, over everything the game plays. Not a row in this window: the game's own Options screen sets it while you play (below); `--set volume=…` sets it here |

On a display with a pixel density of 1 the same list names the sizes by their own pixels (720p (1280 × 720),
1280 × 800 (recommended), 1080p (1920 × 1080), …): the list always says what is drawn, so there is nothing to
add up. Under the choices the window says, in plain words, what they come to on this display: the pixels the
picture is drawn at and the size in points of the window (the standard 1280 × 800 picture at Automatic is a
1280 × 800-point window on a 2056 × 1329-point Retina display, drawn at 2560 × 1600 pixels; at a sharpness of
1× it would be a 640 × 400-point window). It says when the game is open and what the buttons will do:

- **Save** writes the file. The one it replaces is kept beside it as `settings.conf.previous`. Keys the app
  does not manage (`GAME_DIR`, `DISC_DIR`, `EXE`, `POINTER`, `QUIT_GRACE_MS`, …) are kept as they were.
- **Save and Play** (or **Save and Restart Game** when the game is open) saves, asks a running game to quit the
  way Cmd-Q does (so the game saves as it ends, the same path as closing it yourself), waits for it, and opens
  it again. It waits up to 25 seconds: a game at a moment that ignores a quit (the opening films, loading)
  ends itself after `QUIT_GRACE_MS` (15 seconds unless the file says otherwise), as it does when closed by
  hand. If it is still there after that, the app says so and does not open a second copy.
- **Recommended** puts the choices that suit this Mac in the window (Window, the standard picture size at
  Automatic sharpness, so the window is 1280 × 800 points on a Retina display, 60 pictures a second, sound on);
  Save makes them the file's. It never touches saved games, profiles or the game's own registry. A settings
  file that leaves `RENDER_SCALE` empty (or out) is Automatic for the launcher as well, so a file saved with
  nothing chosen and one that was never made give the same window.
- **Show Settings File** and **Show Logs** open Finder at them.

A `settings.conf` made by an earlier build is read as it stands (including `PICTURE=4k`, which shows as
1920 × 1080 at a sharpness of 2×, named 4K (3840 × 2160)); saving it writes the same picture in the new form.
One thing changed with the Automatic sharpness: an older file that leaves `RENDER_SCALE` out, which used to be
drawn at 1× (a 640 × 400-point window on a Retina display), is now Automatic (a 1280 × 800-point window there).
Writing `RENDER_SCALE=1` brings the small window back.

Without a window, for tests and scripts: `BlackWhiteSettings --selftest` (checks the reading and writing of
the file), `--print`, `--window-size`, `--list-resolutions` (the Resolution list as the window words it, each
with the `resolution=` value it is set by), `--game-menu` (what the game's own Options screen is given, below)
and `--set screen=… resolution=WxH|native sharpness=auto|1|1.5|2|3 fps=… sound=on|off volume=0..100`, which with
`--restart-game` also quits a running game and opens it again, as Save and Restart Game does.
`BW_APP_SUPPORT_DIR` and `BW_APP_LOGS_DIR` move the folders it uses, as for the launcher.
`native/app/tests/settings-app.sh` checks the app against the launcher in a scratch folder: what the app writes
is read back by `launcher.sh` as the app meant, an earlier file's other keys survive a save, and the game's
Options screen is given the same list the window shows.

### In the game

The Settings app is for before the game starts. Once the game is open, its own Options screen (Esc, then the
Options tab, or Options at the title screen) is the original page with four rows added, set out the way the
original sets its own page out — one column down the middle of the panel, everything centred, a small name
above each added bar:

              Sound Options

           [    SFX Volume    ]
           [   Music Volume   ]
                  Sound
           ◀       On         ▶
               Master Volume
           ◀       100%       ▶

              Video Options

           ◀  Maximum Detail  ▶
                 Screen
           ◀     Window       ▶
               Resolution
           ◀  2560 x 1600     ▶
        A new resolution needs a restart.     (becomes the Apply button once a size is chosen)

           [ ] AutoSave      [ ] Push Scrolling
    Back                                        Quit

The arrows step through the same lists, with the same names, as the Settings window where they overlap (the
game's font has no multiplication sign, so it reads "x"). The two sliders and the detail level are the game's
own, untouched, in their original places. When the game is running with no sound session at all, the page is
the game's own, exactly as the original sets it; the added rows come with the sound session, as there always
is when the game is started through the app.

What takes effect when:

- **Detail** at once, as in the original.
- **Sound** (On, Off) and **Master Volume** (0 to 100, in steps of ten) at once. They are the host's gain
  over everything the game plays, one more multiplier after the game's own mixing: the game sends a volume
  for every sound it plays, its own SFX and Music sliders among them, and these two rows turn the whole of
  it up, down or off on the spot. Both are saved (`AUDIO`, `VOLUME`), so the next start sounds the same. One
  limit: a game started with Play sound off has no sound device open, so it stays silent until the next
  start whatever Sound then says — the row still says what the next start will do.
- **Screen** (Window, Full screen) at once. How the window is shown is the host's choice, not the game's (the
  game always has a window as big as its picture), so the choice goes to the window layer, which moves the
  window into or out of full screen on the spot. It is saved to `settings.conf` as well, in the background
  through `Black & White Settings --set screen=…`, so the next start has it.
- **Resolution** after a restart, and the page says so. The game makes its picture at the size it reads from the
  settings file once, at start-up, and has no way to change it afterwards. Apply starts `Black & White Settings`
  with `--set … --restart-game`, which writes `settings.conf`, quits the game the way Cmd-Q does (the game saves
  as it ends) and opens it again. The game starts at its title screen, as it does after any quit. A size that is
  chosen but not applied is dropped when the page is left, and nothing is written for it until Apply is pressed.
  If the Settings app cannot restart the game, the button comes back saying so.

How it is put in (`native/bw-native/src/display_menu.cpp`): the Options page is the game's
`MiniDialogBoxOptions`; its `Init` and `InitControls` (vtable slots 0 and 8) and its callback are replaced by
host handlers that run the original and then add, place and read the new controls, which are made with the game's
own constructors on its own heap. `launcher.sh` gives the game the list (`BW_DISPLAY_MENU`, from
`BlackWhiteSettings --game-menu`) and the app to apply it with (`BW_SETTINGS_TOOL`); without both nothing is
installed and the page is the original, which is how every run that is not made through the app goes (tests,
parity runs). The Sound and Master Volume rows set the one master gain of the port's own mixer
(`recomp::audio::GetMixer().set_master`, by way of `display_menu.cpp`), which is where the game's own audio
ends up: the game's audio library calls are answered in `hle_qmixer.cpp`, which gives the mixer a voice for
every sound with the volume and place the game asked for, so the game's SFX and Music sliders act inside the
game exactly as they did, and the two new rows multiply over the result. The launcher passes the saved
`VOLUME` back as `BW_MASTER_VOLUME`, which the mixer starts from. A game whose `AUDIO` is off opens no
device at all, so there is nothing for the gain to let through until the next start. The launcher works the list out again at every start, and the Settings app opens the game again
without the values the first game was started with (LaunchServices would otherwise hand the new game this
program's whole environment), so the rows of the restarted game start from the choices just written. The Screen
choice goes through `SetHostFullscreen` in SwARc's window layer (`user32_window.h`), which changes how the
windows that cover the screen are shown (window, full screen on the desktop, or the display's own mode) and
applies it at once; at start the same policy is whatever `BW_FULLSCREEN` or the configuration says.

The main menu (at the title screen, and on Esc in the game) is also arranged a little differently from the
original: Start Skirmish Game and Join Online Game are not in its main column, which reads Continue Game,
Options and Quit Black & White. They live under an **Online** tab at the top, under a "Coming soon" heading,
because skirmish and multiplayer are not part of this port yet. The buttons are still the game's own and do
what they always did if pressed; the tab is just where they are kept until online play is worked on. The main
column also gains two buttons, **Save / Load** and **Inside Temple**, between Continue Game and Options,
once your Temple is built (until then there is no Temple to go into, and the column closes up without
them): Save / Load takes you into the Temple's Save Game room, where saving and loading always lived, and
Inside Temple takes you inside the Temple itself — both by the game's own way in
(`GGame::GoInsideCitadel`), so everything after the click is the original's. How it is put in (`native/bw-native/src/main_menu.cpp`): the
same way as the Options page above — host handlers on the menu's `Init` and `InitControls` and on its
callback, the game's own controls — and only when `launcher.sh` starts the game (it sets
`BW_MAIN_MENU=online`). A game started any other way (tests, parity runs) gets the original five-button menu.

### Picture size

The game thinks in one **logical** size (`RESOLUTION`, written to the registry as `screenw` / `screenh` at
each start). The Mac build draws that picture into a larger image when `RENDER_SCALE` is above 1 and shows it
in the window or on the screen with its shape kept. The **interface does not scale**: menus and hand stay
pixel-sized as at the logical size, only drawn larger on screen.

| `PICTURE` | Logical size | Render scale | Picture drawn |
| --- | --- | --- | --- |
| `classic` | `RESOLUTION` (default 1280×800) | `RENDER_SCALE` (empty or `auto`: the display's density, 2 on a Retina display, 1 on others) | the size times the scale |
| `native` | Main display size in points, rounded down to even numbers (replaces `RESOLUTION`) | the same | the size times the scale |
| `1440p` (older) | 1280×720 | `RENDER_SCALE` (empty: 2; `auto`: the display's density) | 2560×1440 at the default |
| `4k` (older) | 1920×1080 | the same | 3840×2160 at the default |

`RENDER_SCALE` counts with every picture. The Settings app's Resolution list is the same thing in plain
terms: each entry is named by the last column (the size times the scale), so "4K" is 1920×1080 at a scale of 2
and "1440p" is 1280×720 at a scale of 2; there is no separate preset to pick. A 16:9 picture (1280×720,
1920×1080) is **letterboxed** (bars above and below) on a 16:10 display when the picture fills the screen.

How the picture is shown depends on `SCREEN_MODE`:

- `window` (the default): with a render scale above 1 the window has that many of its own pixels for
  each logical pixel, so the larger picture shows one to one. On a Retina display the 1920×1080 picture at
  Automatic (2) is a 1920×1080-point window (3840×2160 pixels, "4K" in the Resolution list), the 1280×720
  one a 1280×720-point window ("1440p"). A window larger than the display's usable area is shrunk, its
  shape kept, to fit, and it is centred. At a scale of 1 the window has one window pixel for each picture
  pixel, which is a small window on a Retina display (1280×800 pixels is 640×400 points).
- `desktop`: the window fills the screen and the picture is fitted into it with its shape kept.
  `native` is meant for this mode.
- `exclusive` has not been tried with the larger pictures. It asks for the smallest display mode
  that holds the logical size, which would be a lower mode than the display's own; use `desktop`
  instead.

Checked by eye on this Mac (display set to 2056×1329 points) before the Settings app existed: `4k` in a
window, 1920×1112 points with the title bar, centred, sharp; `4k` in `desktop`, fitted with bars above and
below; both held a steady 60 pictures a second at the menu.

Checked by script with `check-sizes.sh` (below) on the same display: a resumed Land 2 saved game in a scratch
folder, settings written by the Settings app's own `--set`, the window read from the window system after 100
seconds and compared with the figure the Settings app gives. Every window matched, the game was in play at the
end, and no run wrote a `FATAL` line:

| Resolution (the picture) | Sharpness | Window (points) | Drawn at (pixels) | Pictures a second, no limit |
| --- | --- | --- | --- | --- |
| 1280 × 800 | 1× | 640 × 400 | 1280 × 800 | about 135 |
| 1280 × 800 | 2× | 1280 × 800 | 2560 × 1600 | about 130 |
| 1440 × 900 | 1× | 720 × 450 | 1440 × 900 | about 133 |
| 1680 × 1050 | 1× | 840 × 525 | 1680 × 1050 | about 130 |
| 1920 × 1200 | 1× | 960 × 600 | 1920 × 1200 | about 95 |

The frame rates are a floor, not a benchmark: other apps were using the Mac's memory during much of the run

Mac. None of these has been played by hand: the pointer in the larger windows, the feel and
the sound are unchecked.

**Automatic is what the launcher does** when `settings.conf` leaves `RENDER_SCALE` empty or out: the display's
own pixel density, which is 2 on a Retina display (a 1280 × 800-point window for the standard picture, drawn
at 2560 × 1600) and 1 on a display that is not. An earlier build's file that left it out gave a 640 × 400-point
window on a Retina display; `RENDER_SCALE=1` gives that back. The Settings app's **Recommended** is the standard
picture at Automatic.

`BW_APP_PRINT_SETTINGS=1` prints the derived `RESOLUTION` and `BW_RENDER_SCALE` without starting the
game (`native/app/tests/picture-settings.sh` runs the cases).

## Saves, settings, and reset

- **Settings:** `~/Library/Application Support/Black & White/settings.conf`, written by the Settings app (the
  file it replaces is kept beside it as `settings.conf.previous`)
- **Data (default):** `~/Library/Application Support/Black & White/data` (`DATA_DIR` overrides)
- **Profiles and saves:** `data/bw/install/Profiles/` under that data folder
- **Registry:** `data/bw/registry.txt`
- **Staged install and disc:** `…/Black & White/Game`, `Disc`, `Disc.volume` (from `stage-game.py`)
- **App defaults:** `Contents/Resources/defaults.conf` inside the bundle
- **Logs:** `~/Library/Logs/Black & White/` (ten newest `native-*.log` files)

What resets what:

- **Settings only:** **Recommended**, then **Save**, in the Settings app (or delete `settings.conf`; the
  next start writes a new one). Saved games, profiles and the game's registry are not touched. A change of
  settings only ever changes the picture width and height lines of the registry, at the next start.
- **Everything the game keeps** (saves, profiles, its registry): quit the game, then delete or rename `data/`,
  or individual entries under `Profiles/`. Nothing here does that by itself.

Run `stage-game.py` again to refresh staged game folders.

## Known problems

- **Autosave:** ~**0.5 s** pause each time (~every ten minutes at the default interval).
- **Start-up crash:** a rare crash at start-up (about **1 start in 45**) was traced and fixed; 150 starts in a row (hidden window, a fresh data folder each) then ran with none. Not repeated by hand in a visible window.
- **Sound and movies:** verified by programs only, not by ear or eye.
- **Larger pictures:** every size and sharpness the Settings app offers opens a window of the size it says and reaches a saved game in scripted, hidden runs (table above), and the older `PICTURE=1440p` and `4k` ran the heaviest known scene (Land 4) at about 120 pictures a second in hidden runs. None has been played by hand, so the pointer in the new windows, the feel and the sound at 4K are unchecked, and the two largest pictures (1920 × 1200 at 2×, this display at 2×) ran at about 55 to 60 pictures a second while the Mac was short of memory.
- **Black edge:** the last column and row of the picture are black, as in the original (the game's own 2D clip window ends at width − 2 and height − 2).

## Testing the launcher without taking over the screen

`BW_APP_DRYRUN=1` prints what would be started and does not start it. `BW_APP_SUPPORT_DIR` and
`BW_APP_LOGS_DIR` replace the two folders under `~/Library`, and `BW_APP_NO_DIALOG=1` prints the
messages instead of showing dialogs. `BW_BACKGROUND=1` (test mode: no focus, the real mouse and
keyboard are ignored) is passed through to the game, as are the other `BW_*` switches
(`BW_TEST_INPUT`, `BW_SHOT_DIR`, `BW_AUDIO`, `BW_FPS_CAP`, `BW_QUIT_GRACE_MS`, …).
`BW_SETTINGS_BIN` names the Settings app's program for the list the game's Options screen is given (the
launcher otherwise looks beside itself and in `~/Applications`); a game opened again by the Settings app
(Apply in the game, Save and Restart Game) gets the test's switches but not the values the launcher works out.

`native/app/check-sizes.sh` runs the game in the background at chosen screens, picture sizes and sharpness (for
example `check-sizes.sh s2:window:1280x800:2 w4k:window:1920x1080:2`). For each case it writes the settings with
the Settings app's own `--set`, starts the game through the launcher in a scratch folder with a resumed saved game,
reads the window's size from the window system after 100 seconds, takes a picture of the window, and compares
the window with what the Settings app says (`--window-size`). It prints one line per case with PASS or FAIL
(the game did not start, ended early, wrote a `FATAL` line, or opened a window of another size) and the median
frame rate of the game's ten-second reports, which is only a floor: it falls when the Mac is busy with other
work, and the verdict does not depend on it. It waits for the machine's gate and for any other game window to
close, and it never touches the player's settings, saves or logs. `-a` and `-s` name the game app and the
Settings app (the installed ones by default).

To test the path a double-click takes, start the app through LaunchServices with the switches given by
`open --env`, and keep every file the game must read outside Desktop, Documents and Downloads (the
scripted input and screenshot folder too):

```
open -n -g --env BW_BACKGROUND=1 --env BW_APP_SUPPORT_DIR=/tmp/bw/support --env BW_APP_LOGS_DIR=/tmp/bw/logs \
     --env BW_TEST_INPUT=/tmp/bw/script.input --env BW_SHOT_DIR=/tmp/bw/shots --env BW_SHOT_EVERY=450 \
     --env BW_AUDIO=wav:/tmp/bw/out.wav --stderr /tmp/bw/open-stderr.txt "$HOME/Applications/Black & White.app"
```

(`mkdir -p /tmp/bw/shots` first; the runtime does not make the screenshot folder. Stop the game with
`pkill -f "Black & White.app/Contents/MacOS/bw_native"`. Take a turn with the other runs that show a window.)

## Not done yet

- Older macOS: this build needs macOS 27 (the bundled libraries are built for 26 to 27.2).
  A build for older systems means rebuilding every bundled library with a lower deployment
  target, and none has been tested.
- Creature Isle is not supported yet (see "The short way (playing)"): its build does not
  start reliably, so the expansion is refused at set-up for now.
- The app is not notarised, so a downloaded copy needs the Open Anyway step above.
- Nothing the Settings app offers has been played by hand: the sizes at a sharpness of 1× and 2× were run by
  script (`check-sizes.sh`), the app's window and its Save and Restart Game button were driven through the
  accessibility interface, and the game's own Screen and Resolution rows were driven by scripted clicks and
  read from the game's own pictures (the 1280 × 800 window with sound, the 1920 × 1080 window without, the
  title screen's Options page) and its logs (Apply, then the restart into a window and into full screen at
  the new size), not by a person. Full screen was looked at in scripted runs only.
- Foreground double-click (focus, Dock, real input, speaker audio) not watched end-to-end; tests use
  `BW_BACKGROUND=1`.
